# PZSA-2026-003: keystone (keystone-classic) 4.0.0 to 4.2.1: CSRF validation passes for sessions that hold no CSRF secret

> Identifier in the report sent to the maintainers: KS-001.

## Summary

The npm package `keystone` 4.x (Keystone "classic") is a Node.js content management system and web application framework. Its repository was archived by the maintainers in February 2022 and superseded by Keystone 6 (`@keystone-6/core`), a different code base that is not affected. In keystone 4.0.0 to 4.2.1 the CSRF validation of the Admin UI API does not fail when the session holds no CSRF secret: the expected token then depends on the salt alone and is a constant an attacker can precompute. Sessions regenerated at sign-in are in that state until an Admin UI page is rendered, so a page on another origin can perform write operations in the Admin UI as the victim and can sign a visitor in to an attacker-controlled account. The gap survived the fix for CVE-2017-16570. There is no fixed version; a patch and mitigations are provided.

## Affected versions

- 4.2.1 (npm), verified; identical to commit 6e5ba1142 of keystonejs/keystone-classic.
- 4.0.0 to 4.2.0 believed affected: `lib/security/csrf.js` has not changed since the fix for CVE-2017-16570 (PR #4478, merge f08baa4f, 2017). Not individually tested.
- No fixed version: the repository was archived in February 2022.

## Methodology

Source review of keystone-classic at commit 6e5ba1142, which is identical to the npm release 4.2.1. The behaviour of `validate()` with a session that holds no secret was confirmed by calling an exact mirror of the function in isolation (see Proof of concept). Not reproduced on a running instance.

## Technical analysis

Keystone's CSRF scheme is the usual salt-plus-hash-of-secret construction. `createSecret()` stores a random secret in `req.session._csrf_secret`; `createToken()` emits `salt + sha1(salt + secret)`; `validate()` recomputes the hash from the salt prefix of the submitted token and compares with `scmp`.

The flaw is that `validate()` (`lib/security/csrf.js:61-77`) never checks that the session actually holds a secret:

```js
return scmp(token, tokenize(token.slice(0, exports.SECRET_LENGTH), req.session[exports.SECRET_KEY]));
```

When `req.session._csrf_secret` is `undefined`, `tokenize()` concatenates `salt + undefined`, i.e. the literal string `"undefined"`. The expected value therefore becomes a constant function of the salt alone, with no per-session input. A token built as `salt + sha1(salt + "undefined")` is accepted by every session in that state, and the state is reachable in normal operation because the secret is only written when an Admin UI page is rendered:

- `getSecret()` is called from `createToken()`, which is called from `getToken()`, which is only invoked by the server-rendered index and sign-in pages (`admin/server/routes/index.js:57`, `admin/server/routes/signin.js:21`). No API handler creates the secret.
- `session.signinWithUser()` calls `req.session.regenerate()` (`lib/session.js:49`) before storing `userId`. The regenerated session has no `_csrf_secret`. This happens on every sign-in through `POST /api/session/signin`, through `keystone.session.signin()` from application code, and through the persistent `keystone.uid` cookie handled by `session.persist` (`lib/session.js:186-216`), which signs the user in on the first request of a new session.
- Until that signed-in user next loads an Admin UI HTML page, every CSRF-protected POST handler accepts the constant token above: `admin/server/api/list/{create,update,delete}.js`, `admin/server/api/item/{update,sortOrder}.js`, `admin/server/api/session/{signin,signout}.js`, `admin/server/api/s3.js`. Clients that only talk to `/keystone/api/*` (custom front-ends, mobile apps, scripted sign-in) can stay in that state indefinitely.
- `POST /api/session/signin` is mounted before the auth middleware (`admin/server/app/createDynamicRouter.js:47-49`) and is reached by sessions that have never rendered a page, so its CSRF check is void for a visitor who has not opened the sign-in page (login CSRF).

Two secondary issues in the same file: `createSecret()` uses the deprecated `crypto.pseudoRandomBytes` (`lib/security/csrf.js:25`), and `validate()` does not check the token length, so the comparison runs on attacker-chosen lengths (CWE-347, Improper Verification of Cryptographic Signature).

The `DISABLE_CSRF` environment switch (`lib/security/csrf.js:9`) is unrelated and documented; it must stay unset for any of this to matter.

## Impact

A page on another origin that can make the victim's browser send the Keystone session cookie can execute, as the victim, every Admin UI write operation guarded only by `csrf.validate()`: create, update and delete items in any list, change sort order, sign out, upload to S3. The preconditions are that the victim holds a signed-in session with no stored CSRF secret (see above) and that the browser attaches the cookie to a cross-site request. express-session is configured by `lib/core/initExpressSession.js` without a `sameSite` attribute; whether a cross-site top-level POST carries the cookie therefore depends on the browser's default (Chromium applies Lax by default with a two-minute exception after the cookie is set; Firefox and Safari behave differently) and on any `session options` the operator supplied.

Login CSRF: a visitor with no session can be signed in to an attacker-controlled Keystone account without a valid token.

CVSS rationale: AT:P because exploitation needs a signed-in session that has not rendered an Admin UI page since sign-in and a browser that attaches the session cookie to the cross-site request; UI:P because the victim only has to load the attacker's page; VI:H because the attacker can create, modify and delete items in any list. The CVSS 3.1 vector expressed the same preconditions as AC:H.

## Proof of concept

Node.js only, no Keystone instance needed. `tokenize()` and `validate()` are exact mirrors of `lib/security/csrf.js`; the real `validate()` differs only in using `scmp` for the comparison.

```js
const crypto = require('crypto');
const tokenize = (salt, secret) => salt + crypto.createHash('sha1').update(salt + secret).digest('hex');
const validate = (session, token) => token === tokenize(token.slice(0, 10), session._csrf_secret);

const forged = tokenize('AAAAAAAAAA', undefined); // sha1("AAAAAAAAAAundefined"): a constant
console.log(validate({}, forged));                              // true: accepted by any session without a secret
console.log(validate({ _csrf_secret: 'per-session' }, forged)); // false
```

Submitting the constant token as `_csrf` in a POST to a protected API route, under a session in the state described above, passes the check.

## Remediation

No upstream fix. The patch `PZSA-2026-003/0001-csrf-fail-closed-when-session-has-no-secret.patch` changes `lib/security/csrf.js` so that:

- `validate()` returns `false` when `req.session[SECRET_KEY]` is not a non-empty string, instead of hashing against `"undefined"`;
- tokens whose length is not `SECRET_LENGTH + 40` are rejected;
- `createSecret()` uses `crypto.randomBytes`.

Callers are unchanged; a session without a secret now fails the check until an Admin UI page has been rendered, which is what the design assumed.

Mitigations for operators:

- Apply the patch to `node_modules/keystone/lib/security/csrf.js` (patch-package or a fork).
- Alternatively register a `pre:adminroutes` middleware that answers 403 to any non-GET/HEAD/OPTIONS request whose `req.session._csrf_secret` is missing.
- Set an explicit `sameSite` on the session cookie via `keystone.set('session options', { cookie: { sameSite: 'lax' | 'strict', secure: true } })` so the outcome does not depend on browser defaults.
- Leave `cookie signin` disabled in production (it is off by default outside `development`, `index.js:62`); it is the path that most often produces long-lived sessions without a secret.
- Never set `DISABLE_CSRF` outside local development.
