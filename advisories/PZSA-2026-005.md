# PZSA-2026-005: keystone (keystone-classic) 4.0.0 to 4.2.1: Session API returns the raw user document, including the bcrypt password hash

> Identifier in the report sent to the maintainers: KS-003.

## Summary

The npm package `keystone` 4.x (Keystone "classic") is a Node.js content management system and web application framework, archived by the maintainers in February 2022 and superseded by Keystone 6 (`@keystone-6/core`), a different code base that is not affected. Two handlers of the Admin UI Session API serialise the Mongoose user document directly, so the response to the signed-in user contains the bcrypt hash of their password and every other attribute of the account. Everywhere else the Admin UI serialises users through a layer that replaces the hash with a boolean. There is no fixed version; a patch and mitigations are provided.

## Affected versions

- 4.2.1 (npm), verified; identical to commit 6e5ba1142 of keystonejs/keystone-classic.
- 4.0.0 to 4.2.0 believed affected, not individually tested.
- No fixed version: the repository was archived in February 2022.

## Methodology

Source review of keystone-classic at commit 6e5ba1142, identical to npm 4.2.1. Not reproduced on a running instance.

## Technical analysis

- `GET /<admin path>/api/session` answers `res.json({ user: req.user })` (`admin/server/api/session/get.js:2`).
- `POST /<admin path>/api/session/signin` answers `res.json({ success: true, user: user })` on success (`admin/server/api/session/signin.js:23`).

`res.json` calls the document's `toJSON()`, which emits every schema path. The `Password` field type stores the bcrypt hash in the document under the field path (`fields/types/password/PasswordType.js`, `addToSchema`), so the hash is in the response, together with any other field on the user model (API keys, reset tokens, internal flags). Everywhere else the Admin UI serialises users through `List.getData()` (`lib/list/getData.js`), which delegates to each field type's `getData()`; the Password type's implementation (`PasswordType.js:133`) returns a boolean presence flag rather than the hash. The Session API bypasses that layer (CWE-200, Exposure of Sensitive Information to an Unauthorized Actor).

Both routes are mounted before the authentication middleware (`admin/server/app/createDynamicRouter.js:47-48`), but `req.user` is populated from the session, so only the caller's own document is returned. The endpoint is called by the Admin UI client on load and the sign-in response is kept in the client's state.

`admin/server/api/Readme.md` documents the response as `{ user: req.user }`, so the maintainers may consider this intended behaviour.

## Impact

The password hash and every other attribute of the signed-in account are exposed to anything that can read Admin UI responses: a party holding the session but not the password (shared workstation, stolen cookie, cross-site scripting anywhere on the origin), browser extensions, corporate proxies and logging or caching layers that see the body, debugging tools, and the browser's own memory and disk caches. The hash is then available for offline guessing; bcrypt slows but does not prevent that for weak passwords, and a recovered password outlives the session and may be reused elsewhere. The persistent sign-in cookie `keystone.uid` is derived from the hash (`lib/session.js:54`), but it also requires the server's `cookie secret`, so the leak alone does not forge it.

CVSS rationale: PR:L because the caller needs a signed-in session; the relevant attacker is one who holds a session without knowing the password. VC:L because one account's hash and attributes are exposed per session.

## Proof of concept

With the session cookie of a signed-in Admin UI user:

```
curl -s -b "<session cookie>" "https://TARGET/keystone/api/session"
```

The `user` object in the response contains the `password` field with the bcrypt hash (`$2a$10$...`), whereas `GET /keystone/api/users/<id>` returns `"password": true` for the same account.

## Remediation

No upstream fix. The patch `PZSA-2026-005/0003-session-api-do-not-expose-raw-user-document.patch` makes both handlers return `UserList.getData(user)` (falling back to `{ id }` if the list cannot be resolved). The password field becomes the same boolean the rest of the Admin UI already receives; the Admin UI client only uses `id`, `name` and field presence from this response.

Mitigations for operators:

- Apply the patch to `node_modules/keystone/admin/server/api/session/{get,signin}.js`.
- Or set a `toJSON` transform on the user schema (`User.schema.set('toJSON', { transform: (doc, ret) => { delete ret.password; return ret; } })`) in the model file; this also covers any application code that serialises the document.
- Or register a `pre:adminroutes` middleware that handles `GET /api/session` itself and returns a reduced object.
