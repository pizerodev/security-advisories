# PZSA-2026-006: keystone (keystone-classic) 4.0.0 to 4.2.1: Cloudinary upload API accepts POSTs without a CSRF token

> Identifier in the report sent to the maintainers: KS-005.

## Summary

The npm package `keystone` 4.x (Keystone "classic") is a Node.js content management system and web application framework, archived by the maintainers in February 2022 and superseded by Keystone 6 (`@keystone-6/core`), a different code base that is not affected. The Admin UI exposes two image upload handlers for the TinyMCE editor; the S3 handler validates the CSRF token, the Cloudinary handler does not. A page on another origin can therefore upload arbitrary files into the operator's Cloudinary account under an administrator's session. There is no fixed version; a patch and mitigations are provided.

## Affected versions

- 4.2.1 (npm), verified; identical to commit 6e5ba1142 of keystonejs/keystone-classic.
- 4.0.0 to 4.2.0 believed affected, not individually tested.
- No fixed version: the repository was archived in February 2022.

## Methodology

Source review of keystone-classic at commit 6e5ba1142, identical to npm 4.2.1. Not reproduced on a running instance.

## Technical analysis

The two Admin UI image upload handlers used by the TinyMCE `uploadimage` plugin (`fields/types/html/HtmlField.js:171`) are asymmetric:

- `admin/server/api/s3.js:12-14` begins with `keystone.security.csrf.validate(req, req.body.authenticity_token)` and answers 403 on failure.
- `admin/server/api/cloudinary.js:6-36`, mounted at `POST /<admin path>/api/cloudinary/upload` by `admin/server/app/createDynamicRouter.js:80`, has no call to `csrf.validate` at all. It takes `req.files.file` (parsed by the multer instance configured in `lib/uploads`), optionally derives `public_id` from the client-supplied `originalname` when `wysiwyg cloudinary images filenameAsPublicID` is set (`:13-15`), and calls `cloudinary.uploader.upload()` with the server's account credentials.

The route is registered only when `cloudinary config` is set and, with `auth: true`, sits behind `keystone.session.keystoneAuth`, so it executes for any request carrying a signed-in administrator's session cookie. A plain HTML multipart form on a foreign origin satisfies the handler's input requirements; nothing in the request has to be derived from the victim's session. `admin/server/api/Readme.md` states that all POST API endpoints are protected with CSRF; this handler is the exception.

## Impact

If the victim's browser attaches the Keystone session cookie to a cross-site POST (see PZSA-2026-003 for the `sameSite` discussion; express-session is configured without the attribute in `lib/core/initExpressSession.js`), a third-party page can upload arbitrary files into the operator's Cloudinary account under the administrator's session. Consequences are storage and bandwidth consumption on the operator's account, hosting of attacker content on the operator's Cloudinary URLs, and, when `filenameAsPublicID` is enabled, control over the public ID, which may replace existing assets with the same ID depending on the account's overwrite settings. No Keystone data is modified; the authorised administrator's session is used as the authority.

CVSS rationale: AT:P because the browser must attach the session cookie to the cross-site request, which depends on browser defaults and operator configuration; UI:P because the victim only has to load the attacker's page. Keystone's own data is unchanged, so the impact is scored on the operator's Cloudinary account as the subsequent system (SI:L). The CVSS 3.1 vector expressed the cookie precondition as AC:H.

## Proof of concept

With the session cookie of a signed-in administrator, on an installation where `cloudinary config` is set:

```
curl -s -b "<session cookie>" -F "file=@image.png" "https://TARGET/keystone/api/cloudinary/upload"
```

succeeds without any CSRF token, whereas the same request to `/keystone/api/s3/upload` without `authenticity_token` is answered 403.

## Remediation

No upstream fix. The patch `PZSA-2026-006/0005-cloudinary-upload-require-csrf-token.patch` makes the handler validate the token from the standard locations (`_csrf` body or query, `X-CSRF-Token` or `X-XSRF-Token` headers) or from `authenticity_token`, mirroring `s3.js`, and answer 403 `{ error: { message: 'invalid csrf' } }` otherwise. The TinyMCE plugin already sends the token, so the Admin UI is unaffected. Apply it together with the patch of PZSA-2026-003, otherwise the check inherits the no-secret bypass described there.

Mitigations for operators:

- Apply the patch of PZSA-2026-003 and the patch above.
- Or add a `pre:adminroutes` middleware that rejects `POST /api/cloudinary/upload` unless `keystone.security.csrf.validate(req)` passes.
- Set `sameSite` on the session cookie via `session options`.
- Leave `wysiwyg cloudinary images filenameAsPublicID` disabled; prefer S3 uploads if Cloudinary is not needed by the WYSIWYG field.
