# PZSA-2026-001: typicms/core 16.0.5 to 17.0.45: exposure of every user's API token through the users and history API

## Summary

[TypiCMS](https://github.com/typicms/core) is a multilingual content management system built on Laravel and distributed as the Composer package `typicms/core`. In versions 16.0.5 to 17.0.45 the users API and the history API return the `api_token` column of every user whenever the client omits the optional `fields[...]` query parameter. Any back-office account that holds the `read users` or `see history` permission can read the static bearer token of a superuser and use it against the whole API. Fixed in 17.0.46.

## Affected versions

- 17.0.45, verified on a local installation (commit ed20bda9).
- The same code is present from 16.0.5: `allowedFields()` is used without an explicit column list, and `api_token` has never been listed in `$hidden` (the property, which only ever held `password` and `remember_token`, was removed in commit 93e35be5 on 2025-06-12). Releases between 16.0.5 and 17.0.44 were not tested individually.
- Fixed in 17.0.46 (commit b79431b205c4, 2026-11-05).

## Methodology

Source review of typicms/core at commit ed20bda9 (release 17.0.45), followed by dynamic testing on a local installation of 17.0.45 with the default configuration: a user whose role carries only the `read users` permission, calling the API with that user's token. The behaviour of the `Historable` trait described under Remediation was checked again on the source of 17.0.56 (the latest release on 2026-11-13).

## Technical analysis

- `src/Models/User.php` declares no hidden attributes, so `toArray()` and JSON serialisation include `api_token`.
- `src/Http/Controllers/UsersApiController.php::index` relies on spatie/laravel-query-builder `allowedFields()`, which does not restrict the selected columns when no `fields` parameter is present; the query is `SELECT users.*`.
- `src/Traits/Historable.php` stores `$model->toArray()`, token included, in the `new` column of the `history` table when a model is created, and `src/Http/Controllers/HistoryApiController.php` returns those rows as stored (CWE-212, Improper Removal of Sensitive Information Before Storage or Transfer).
- Tokens are UUIDs generated once in `User::boot()` and never rotated; the `api` guard is configured with `'hash' => false`, so the stored value is the usable credential.

## Impact

A user with `read users` or `see history` obtains the token of every account, including superusers, and gains full control of the TypiCMS API: user, role, content, file, menu and translation management, and history truncation. The access persists until the tokens are changed by hand.

CVSS rationale: PR:L because any back-office account with one of the two permissions is enough; VC:H, VI:H and VA:H because a superuser token gives complete control of the application through its API. No subsequent system is affected.

## Proof of concept

With a token that only carries the `read users` permission:

```
curl -s -H "Authorization: Bearer <token>" -H "Accept: application/json" \
  "https://TARGET/api/users?per_page=100" | jq '.data[] | {email, superuser, api_token}'
```

A superuser token taken from the response then succeeds on endpoints the original token was denied, for example `GET /api/roles` (403 before, 200 after).

## Remediation

17.0.46 adds `#[Hidden(['api_token'])]` to the `User` model, which removes the token from `toArray()` and JSON output, including the snapshot written to history rows when a user is created. The users API and the history rows written from that point on no longer expose the token. Upgrade to 17.0.46 or later (17.0.47 also fixes PZSA-2026-002).

Three points are not covered by the release and are for operators to handle after upgrading:

- History rows written before the upgrade still contain the serialised token in `history.new` and are still returned by the history API. Strip `api_token` from the existing rows, or truncate the history table.
- Tokens were not rotated by the fix. Any token read before the upgrade is still valid: regenerate the `api_token` of every user.
- The `updated` hook of the `Historable` trait reads the raw attributes (`$model->getAttributes()`, still the case in 17.0.56), so hidden attributes are not filtered on that path: a change of `api_token` made through Eloquent (for example the rotation above) is written to `history.old` and `history.new` in clear and returned by the history API. Rotate the tokens with a direct database update, or apply the patch below, until a release filters hidden attributes in that hook.

For installations that cannot upgrade, the patch supplied with the report (`PZSA-2026-001/0001-Never-serialise-users.api_token-API-responses-histor.patch`) hides the attribute and skips hidden attributes in the history snapshot; a regression test (`PZSA-2026-001/ApiTokenDisclosureTest.php`) is included.
